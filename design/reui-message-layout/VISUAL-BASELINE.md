两张图都是有背景、裁切、渐变或放大卡片的宣传素材，不是同窗口、同内容、同缩放的完整应用截图。它们适合核对层次和关系，不能直接把图像像素换成 CSS px，也不能与原型整窗截图直接做像素差分并宣称 1:1。

## 原型截图条件

- 视口：**1440 × 940 CSS px**；设备像素比 **1**；无额外缩放。
- 浏览器：Playwright Chromium；本轮采集版本 **156.0.8078.4**。后续实际版本及平台写入截图元数据。
- 每组使用新浏览器上下文，默认本地存储为空，不沿用用户偏好。
- 基础外观：浅色、阅读布局、16px 正文、舒适密度；额外采集深色及经典布局。
- 默认保留项目导航和右侧项目浏览器，等待离线「项目概览」标题可见并移开鼠标后采集；不为截图强制刷新页面。
- 从 `?view=new` 开始，输入 **整理消息区的视觉层次**；通过可控时钟检查 700ms 执行中和 1800ms 完成状态，不调用节点或模型。
- 正文与输入框共用既有阅读列；本轮不更改标题栏、侧栏、导航或右侧面板宽度。
- 基础工况下正文阅读列左边界为 **351px**、宽 **518px**。这些是当前原型的测量值，不是从宣传图推导出的目标值。

可重复采集：

```sh
mkdir -p /tmp/rpi-ui-visual-baseline
RPI_WORKBENCH_SHOTS=/tmp/rpi-ui-visual-baseline node design/reui-message-layout/verify.cjs
```

输出包括 `turn-running-light.png`、`turn-complete-light.png`、深色/经典布局、已展开执行过程及失败状态。`turn-hierarchy-metrics.json` 记录浏览器、平台、视口、DPR、主题、布局、密度、计算字体和正文/阅读列几何。输出目录是生成物，不作为仓库内持久的目标截图。

## 已知的独立绘制问题

本轮在 Chromium 156/macOS 观察到：切换主界面为深色后，沙箱预览可能只绘制页头而暂不绘制主体；主体 DOM、几何和计算颜色仍正常。在非控时 HTTP 检查中显式刷新可恢复，控时截图中刷新并不稳定。**等待元素可见不代表其像素已正常绘制；这类深色截图不能用于右侧页面的像素验收。** 本轮不通过强制重载掩盖该现象。后续需区分浏览器重绘与原型原因；不能为绕过它而在用户切换主题时自动刷新真实网页、丢失页面状态。

## 本轮差异与验收

1. **完成回答仍嵌在执行过程里**：原来 `.turn-response` 的左边界为 371px，比阅读列缩进 20px；现将正文移为轮次的直接子元素，基础工况下回到 351px，并随窗口尺寸共享阅读列宽度。
2. **完成步骤抢占正文层次**：已完成步骤默认收进原生 `details/summary` 摘要；最终回答保持可见。执行中、失败和重试入口不被默认折叠。
3. **不以视觉精简牺牲交互**：读者已经展开的工具记录在完成及后台完成后保持可查看；手动收起的完成摘要在切换会话后保持收起。计划完成后的「开始实施」按钮位于摘要外，不被隐藏。
4. **验证边界**：在 1440/1280/1024px 桌面宽度、明暗主题、阅读/经典布局下检查正文几何及键盘展开；这些检查不等于原生应用像素一致。

## 下一次严格对照还需要什么

- 同一目标应用版本、主题、字体、缩放/DPR和窗口客户区尺寸。
- 相同消息内容、执行阶段、面板开关与宽度、滚动位置。
- 未裁切且无宣传渐变叠层的目标应用截图。
- 在上述条件一致后，分别对照外壳、正文、执行摘要、代码/diff 与设置；不要用 TUI 源码或结构测试替代桌面截图证据。
