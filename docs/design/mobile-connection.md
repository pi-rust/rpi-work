# 手机扫码连接 PC · v0.8

> 历史设计稿：包含尚未落地的设备授权方案和已移除的手机高级表单。当前0.1.2手机仅扫码，交互与实现以[节点连接说明](../guides/node-connection.md)为准。

> 截图与运行报告为本地产物，不随Git分发；文中路径用于定位本地文件。保留规则与复验入口见 [测试产物说明](../guides/testing-artifacts.md)。

2026-10-24。默认拓扑明确为 **PC 是服务端，手机是客户端**。PC 保存项目、运行 rpi 与工具、管理模型凭据并持续执行任务；手机连接 PC 的 HTTP API 和事件流，查看进展、发送消息、查看变更或回答确认。

## 1. 两种入口，共用一条配对流程

### 默认：扫码

1. PC 打开「设置 → 执行节点 → 扫码连接手机」，显示可达服务地址、连接二维码、短时有效期和高级模式配对码。
2. 手机扫描二维码，显示目标电脑信息，填写本机设备名并提交请求。
3. 两端展示同一校验码。PC 用户核对后，明确选择项目及客户端权限，点击授权。
4. 手机获得属于此设备的授权，再读取项目/会话快照并订阅事件流。

二维码被识别不代表配对成功；电脑确认前不允许读取项目或发送 Agent 指令。默认邀请有效期示例为 5 分钟；刷新后旧二维码和旧配对码失效，一份邀请只用于一次有效配对流程。

### 高级：手工输入

手机选择「高级 · 手工输入」，填写：

- 完整 PC 服务地址，包括协议和可选端口。
- PC 显示的一次性配对码。
- 本机设备名称。

手工模式进入相同的等待电脑确认、项目授权、会话同步流程。地址和端口只是找到服务，不是授权凭据；不把“保存地址”显示成已经连接成功。后续如增加已授权凭据导入，应该采用另一种明确的凭据流程，不能直接把 provider API Key 当成节点凭据。

## 2. 角色与界面

PC「执行节点」页展示服务角色、可达地址、端口、二维码入口、待确认请求和已授权手机。每个手机分别显示配对状态、在线状态、项目范围和撤销入口。

手机首次连接页提供相机扫码、二维码图片识别、粘贴配对链接和高级输入。连接后展示目标电脑、连接状态、同步游标、已授权项目和会话入口。只读授权仅进入已授权项目的只读预览，不进入可发送指令的编辑流程。

二维码采用标准黑白内容与留白，独立于主题配色，深色主题也不会把它反色或在中心盖装饰图案。原型使用本地打包的 QR 编码/解码库，不把二维码或相机图像发送给第三方服务，来源与许可证见 [vendor/README.md](../../design/prototype/vendor/README.md)。

Web 端相机入口先检查浏览器能力与安全上下文，仅在用户主动点击后请求权限；不可用或拒绝时保留图片/链接/高级输入入口。停止扫描、切换页面、隐藏页面或旧请求失效后释放相机；相机权限晚返回也不能在已经离开的页面继续采集。

## 3. 连接信息与状态

建议的配对链接形状：

```text
https://<pc-address>:<port>/connect#pair=<versioned-invitation>
```

邀请至少绑定版本、节点 ID、随机短时 ticket、到期时间和节点身份信息。QR 使用高熵 ticket；手工短码由服务端映射到同一邀请，并限制尝试次数。不要把永久设备凭据或模型 API Key 放进二维码。

邀请放在 URL fragment 可以减少它进入常规请求日志的机会；真实客户端仍需在受信任的页面中通过受保护连接交换凭据。fragment、显示的指纹或一个有效 QR 图案本身都不构成身份认证。原型的指纹、校验码与授权是交互数据，没有实现密码学握手。

| 维度 | 状态 | 主要行为 |
| --- | --- | --- |
| 邀请 | ready / pending / used / expired | 到期或刷新使旧邀请失效 |
| 请求 | requesting / awaiting / approved / rejected / cancelled | 电脑明确决策；取消不当成授权 |
| 客户端传输 | syncing / online / offline / reconnecting | 重连不自动重发用户 prompt |
| 设备授权 | active / revoked | 撤销后重新获取邀请与电脑授权 |
| Agent 运行 | 独立的运行/等待/结算状态 | 手机断线不改成 Agent 已停止 |

配对、重连和相机各自隔离异步回调。新配对不能继承上一台设备重连成功的回调；撤销后旧的同步回调不能把客户端改回在线。生成新的邀请也不应中断已经授权的其他设备。

## 4. 地址与部署

局域网连接使用手机可达的 PC 地址。手机上的 `localhost` 和 `127.0.0.1` 指向手机自身，不能用来访问电脑。主机名无法解析时应能改用 PC 的可达 IP；示例 `.local` 名称不代表原型提供了自动发现或保证各网络能解析它。

远程连接使用用户已配置的 HTTPS 或受保护网络入口。手机浏览器先要能够访问并信任服务地址，不能用一个 QR 图案绕过网络可达性、TLS 或系统信任要求。原生端与 Web 端的身份信任实现需要分别验证。

正式 PC 端的服务设置需要区分监听地址、监听端口和手机访问地址；反向代理地址也未必等于本机监听地址。开启 LAN 服务是明确的 PC 功能，默认仅本机监听的服务不能被界面悄悄改成公开监听。不要自动开放防火墙、配置端口转发或发布公网入口。

当前 UI 的 HTTP 示例只接受私网 IPv4 或 `.local` 地址；远程地址要求 HTTPS。这只是原型格式校验，不是实际部署的传输安全实现。当前预览仍由 `127.0.0.1:4173` 静态服务器提供，没有把该服务开放给手机。

## 5. rpi-web 与新协议边界

现有 `rpi-web` 已提供会话 HTTP/SSE、快照、命令和登录基础。读取相邻仓库的 `src/security.rs` 与 `src/protocol.rs` 后，本稿继续将**逐设备配对、授权范围、撤销与凭据管理**列为新增能力，不能把现有共享密码登录直接当成已实现的手机配对。

建议在执行节点增加下列概念接口，路径只是提案：

| 操作 | 建议入口 | 调用身份 |
| --- | --- | --- |
| 创建/刷新短时邀请 | `POST /api/v1/pairings` | PC 管理端 |
| 提交设备请求 | `POST /api/v1/pairings/{id}/requests` | 有效邀请持有者，受限流 |
| 查询自己请求的结果 | 请求绑定的状态流或查询入口 | 仅此请求的客户端 |
| 确认/拒绝 | `POST /api/v1/device-requests/{id}/approve` / `reject` | PC 管理端 |
| 已授权设备清单 | `GET /api/v1/devices` | PC 管理端 |
| 撤销设备 | `DELETE /api/v1/devices/{id}` | PC 管理端 |

邀请匹配、到期、使用状态和首次确认必须在服务端原子处理。PC 管理权限与手机客户端权限分开；不能因为手机已经登录就允许它批准新设备。项目过滤和只读约束应在每个 HTTP/命令/事件订阅入口生效，不能只靠前端隐藏按钮。

设备凭据和刷新机制需要支持撤销：撤销设备后拒绝后续命令与刷新，并结束相应事件连接。PC 保留 provider 凭据；手机只保存本设备的连接身份。浏览器和原生端分别选用合适的凭据保护方式，不在日志或二维码中长期暴露它。

配对成功后复用既有流程：能力发现 → 已授权项目/会话 → snapshot → events(after)。客户端游标绑定节点、会话和当前宿主代际。恢复失效重取快照，最终状态仍以 `agent_settled` 为准，详见 [流式消息](streaming.md)。手机前后台切换后的事件恢复也需要真机验证。

## 6. Rust / Dioxus 分工

```text
PC Dioxus UI ── 本机管理身份 ── work-node / rpi-web
                                   │
                                   ├─ pairing / device grants
                                   ├─ session HTTP + SSE
                                   └─ rpi RPC → model / tools / project files
                                           ▲
手机 Dioxus Web / Mobile ── work-client ──────┘
```

- `work-node`：PC 服务生命周期、就绪身份、监听与对外地址管理；手机目标不编译这个能力。
- 节点配对服务：管理短时邀请、待确认请求、设备授权与撤销；记录实际生效的项目范围。
- `work-core`：`NodeEndpoint / PairingInvite / PendingDeviceRequest / DeviceGrant / ClientConnectionState`。
- `work-client`：扫码/手工输入统一产生 `ConnectIntent`，完成配对交换、连接恢复和已有 API 调用。
- UI/platform adapter：PC 二维码、手机扫码/相机/图片选择、平台凭据存储和系统生命周期。

共享 UI 不意味着手机在本地运行工具链。手机发消息、传附件、回答 Ask 或批准命令，都经节点授权后由 PC 执行。只读设备不应通过切换页面或直接调用 API 越权。

## 7. 本次实现与验证

HTML 原型已实现：

- PC/手机角色切换、真实可解码 QR 生成、倒计时与刷新。
- 浏览器相机入口、相机权限失败回退、真实本地 QR 图片解码、链接识别与高级表单。
- 等待 PC 确认、校验码核对、项目/只读或协作授权、拒绝、取消、到期、撤销与重连的本地状态机。
- 按项目显示会话、只读预览、手机断线不停止主 Agent 演示，以及陈旧回调隔离。

**没有实现真实节点配对 API、跨设备状态通信、凭据签发、密码学身份校验或真实 HTTP/SSE 同步。** 相机入口调用真实浏览器 API，测试覆盖权限拒绝、Chrome 模拟视频帧及停止/导航时释放媒体轨道；没有使用真实手机相机进行端到端扫码测试。当前生成的示例 QR 不能据此宣称可以实际连接这台 PC。

`node tests/design/verify-connections.cjs` 独立解码 QR 截图，验证图片识别、手工输入、确认与权限范围、拒绝、过期/旧链接失效、撤销、重连、任务隔离、陈旧回调与 375–1440px 布局；未发生外部 QR、配对或模型网络请求。原有七组浏览器检查继续通过。

记录：`artifacts/connections-validation.json`。截图：PC 二维码（本地生成：`artifacts/prototype-connect-qr-desktop.png`）、手机等待确认（本地生成：`artifacts/prototype-connect-await-mobile.png`）、手机客户端（本地生成：`artifacts/prototype-connect-client-mobile.png`）、高级模式（本地生成：`artifacts/prototype-connect-advanced-mobile.png`）。
