# 头脑风暴文档

> 本文整理 Matrix-Agent 产品与架构讨论，作为后续需求、交互和技术设计的共同起点。
>
> **本文不是当前功能实现清单，也不是已经全部批准的实施计划。**“已对齐共识”“架构建议”“待确认事项”分别标明；实际实现能力以源码和验收结果为准。Matrix-Agent 暂作为产品方向称呼，不代表本轮决定重命名仓库、crate 或应用。
>
> **本轮 grillme 访谈后的优先级：先完成 rpi 的会话资源定制。**用户不需要先创建长期独立的 Agent 对象；新建会话默认使用基础 Package，每个会话采用“一个主 Package + 多个 Skills + 多个 Tools”。下文已修正此前关于多 Package 组合、独立 Agent 生命周期和会话资源升级流程的假设。远程访问、ACP 接入和协作仍保留为产品方向，不等于首版全部实现。

## 一、产品定位【已对齐共识】

项目不是一个固定的 Code Agent，也不只是给 rpi 增加桌面和手机界面。

目标是一个 **可定制、多运行时、多节点的 Agent 使用、开发与协作平台**：

- 使用 rpi 的 Package 功能，每个会话选择一个主 Package，并配置多个 Skills 和 Tools，形成不同用途的执行能力。
- 可以使用 Agent 开发自己的 rpi Package，再经过验证、版本化和部署投入使用。
- 支持多设备 Desktop 相互访问；手机和 Web 作为统一交互入口。
- 支持 Agent 与 Agent 协作，而不只是人与单个 Agent 对话。
- 接入 Claude Code、OpenCode 等其他 Agent，外部 Agent 统一通过兼容的 ACP 接口接入。
- 插件和 UI 扩展是平台的扩展机制；编码只是其中一个应用场景。

一句话概括：

> **Matrix-Agent 统一组织 Agent、项目、会话和任务；rpi 提供原生 Package 定制能力，其他 Agent 通过 ACP 接入；不同节点上的 Agent 可以在授权下协作。**

## 二、核心对象与归属【已对齐共识】

### 2.1 节点、项目、会话

底层归属保持：

```text
Node
└─ Project
   └─ Session
```

- **Node**：执行与权限边界，管理本节点的项目、Agent、会话、任务和资源。
- **Project**：用户工作的组织上下文，不应把所有项目都限定为代码仓库。
- **Session**：属于明确节点和项目的持续交流及其运行上下文。
- **Agent**：会话使用的执行能力，不等同于会话本身；首版不要求用户创建和维护长期独立的 Agent 对象。
- **Task**：一次有目标、状态和结果的工作，可由人提交，也可由 Agent 委派。
- **Run**：任务的一次实际执行尝试。

项目和会话的身份必须携带节点归属，不能只依赖显示名称：

```text
ProjectKey = NodeId + ProjectId
SessionKey = NodeId + SessionId
```

NodeId 不应依赖可能变化的 IP 或 URL。同一个节点的多个连接地址不应制造重复项目。

### 2.2 不建设共享全局会话

这里的“跨节点会话管理”主要指：**一个客户端可以访问和管理不同节点上的会话**，不是让多个节点共同维护一份原生会话历史。

跨节点协作通过任务关联实现：

```text
Node A / Project A / Session A
  → Agent A 委派任务
  → Node B 的 Task
  → Agent B 执行
  → 结果返回 Session A
```

B 是否创建关联会话，由任务执行策略和运行时能力决定；A、B 的会话不会因此自动合并。当前不引入多主会话同步、全局消息排序或透明会话迁移。

### 2.3 会话资源模型【本轮访谈确认】

```text
Node / Project / Session
└─ 会话配置
   ├─ 一个主 Package
   ├─ 多个 Skills
   └─ 多个 Tools
```

- 用户撤回了“自由组合多个平级 Package”的选择；不把它作为需求。
- 不需要先创建“研究 Agent”“写作 Agent”等长期对象，再给它们开会话；直接在新会话中选择和调整资源即可。
- 新建会话默认选好基础 Package，用户可立即输入，不强制先走配置向导。
- 同一项目下，使用不同 Package、Skills、Tools 的会话必须可以并发执行，配置互不影响。
- 三类配置都可以在会话空闲时调整；已有历史保留，修改影响后续执行，不表示旧上下文自动被清除。
- 实际运行隔离和配置应用需要宿主支持；不能仅通过修改前端记录或反复覆盖项目共享配置实现。

**技术状态（rpi 0.14.0 实测）**：已证明同项目不同宿主的工具选择、显式 Skills/提示词参数可区分，且重启同一会话能续用历史；但默认资源发现仍会合并项目/全局资源，当前 Work 创建接口也没有会话资源参数。不能把进程独立当成上述完整资源模型已经交付。详见[能力验证报告](../reviews/rpi-session-resource-validation.md)。

### 2.4 Skills 与工具扩展的获取【本轮访谈确认】

- 界面支持资源下载、导入和安装；Skills、Tools 不必被限制为所选主 Package 的内部列表。
- 工具扩展可以独立安装，再为会话勾选使用；产品概念上，它不算第二个主 Package。
- “主 Package”和“独立工具扩展”的称呼是产品分类；已实测项目 Package 可与显式加载的独立原生扩展组合并执行，但完整会话选集和安装映射仍需补齐，不另造包格式。
- 资源安装先只支持本机：默认全局可用，也可以指定用于某个项目。
- “全局”指本机的资源作用域，不表示分发到所有设备；本轮不要求给其他云节点安装或分发资源。
- 本机资源安装的首版限制，不等于取消远程项目/会话访问的后续方向。
- 原生工具扩展按受信代码处理，允许安装，但必须明确确认来源与风险；不承诺沙箱，也不把工具勾选当成执行隔离。

### 2.5 资源状态与更新【本轮访谈确认】

- 界面的资源状态以 **rpi 实际加载的 Tools、Skills** 为事实来源，不能用下载、导入或本地选择替代加载结果。
- 用户可通过会话的已加载 Tools、Skills 确认当前资源情况。
- 不额外建立一套前端主导的“会话资源版本升级流程”，也不默认要求每个旧会话逐项确认升级。
- 本轮讨论不构成“后台自动检查、下载、安装所有新版本”或“新工具自动在全部会话启用”的需求；资源出现和变化首先依据 rpi 的实际加载机制。
- 已安装、已加载、会话实际启用及 Skill 本轮是否被读取/使用，不应被界面混为同一种状态；当前 RPC 可读工具名和 active tools，但没有对称的 Skills 加载清单。Skills 列表是否进入模型提示词还受 `read` 工具启用状态影响。
- 实测新增 Skill 不会自动进入既有 RPC 宿主；`execute_command /reload` 也不等于 TUI 重载。工具选择在宿主重启后不会自动按上次 `set_active_tools` 恢复；若采用重启应用配置，需要在后续执行前重新应用并核对，不能静默退回更宽工具集。
- 0.15.0 补测确认 `set_active_tools([])` 会让全部已注册工具进入模型请求，不能将空数组显示为“全部禁用”；默认、精确选择、零工具需要明确区分。

### 2.6 首版边界【本轮访谈确认】

首要价值是 **通过 rpi Package、Skills、Tools 定制并使用不同用途的会话**。第一版先完成 rpi 的资源定制；ACP Agent 的资源配置后续再细化，不先强求各运行时具有相同定制体验。

节点互访、Agent-Agent 协作仍是总体方向，但不替代当前的会话主线，也不自动成为这轮首版的必交付内容。

## 三、前端展示：按项目，不按节点展开【已对齐共识】

### 3.1 侧栏平铺不同节点的项目

**数据层级与展示层级分开。**侧栏不必先展开节点，再寻找项目，而是直接展示项目及其会话：

```text
项目                                     ＋

   📁 Matrix-Agent                       …
      代码审阅
      Package 开发

☁  📁 内容工作室                         …
      选题研究
      文稿整理

☁  📁 自动化运维                         …
      服务检查
      部署任务
```

- 本机项目正常展示项目图标。
- 远程项目在项目图标前增加轻量的云端/远程节点标识。
- 会话直接展示在所属项目下面。
- 不额外增加“本机 / 办公室电脑 / 服务器”的强制折叠层。
- 云标识表示“位于其他节点”，不限定为公有云服务器。

### 3.2 悬浮信息与节点详情

鼠标悬浮在节点标识上，展示节点名称、连接状态和远程归属，例如：

```text
执行节点：办公室电脑
连接状态：在线
项目位置：远程节点
```

建议点击或触屏轻点可查看节点详情；移动端不能只依赖 hover。离线、重连和授权失效应有明确状态，不把连接异常表现成项目消失。

同名项目不自动合并，必要时通过节点名称辅助区分。

### 3.3 操作跟随项目所属节点

选中项目后，新建会话、查看文件、提交运行等操作沿用项目的 Node，不让用户反复选择执行位置。

会话工作区应能确认当前节点、Agent、连接状态及工作上下文。消息、草稿、附件、订阅和操作状态按完整会话身份隔离，切换项目或节点不能串数据。

## 四、先从用户能力拆前端【讨论形成的建议】

先定义用户流程与能力，再反推页面、接口和代码模块。**页面不等于模块，内部对象也不必全部成为一级菜单。**

### 4.1 使用主线【本轮访谈确认】

```text
选择项目 → 新建会话（默认基础 Package）→ 直接输入 → 处理交互 → 跟踪执行 → 查看结果
```

### 4.2 会话配置【本轮访谈确认】

```text
打开会话配置 → 选择一个主 Package + 多个 Skills/Tools → 空闲时应用 → 查看 rpi 实际加载结果 → 继续会话
```

用户无需先创建或部署一个独立 Agent。配置变更必须反映到宿主实际状态；请求成功不等于加载确认。

### 4.3 资源获取与 Package 开发

```text
资源目录/导入 → 确认来源及原生代码风险 → 选择本机全局或项目范围 → 安装 → 加载结果 → 会话选择
```

```text
打开 Package 工程 → 在开发会话中提出需求 → 修改 → 测试/构建 → 隔离验证 → 使用或发布
```

开发闭环仍是产品方向，其发布和部署细节不作为本轮已确定需求。

### 4.4 连接与协作【后续方向】

```text
添加节点 → 配对授权 → 获取可访问项目/执行能力 → 提交或委派任务 → 收取结果
```

## 五、前端能力拆分【根据访谈调整】

| 能力域 | 用户需要完成的事情 | 子能力与阶段 |
| --- | --- | --- |
| 项目与会话管理 | 在项目下开始和管理交流 | 主线：项目侧栏、创建、重命名、搜索、置顶、归档恢复、历史；具体生命周期操作归属待细化 |
| 会话工作台 | 完成当前会话交互 | 主线：消息时间线、输入、授权卡片、运行控制、上下文、结果；附件与扩展插槽按实际支持能力逐步加入 |
| 会话资源配置 | 定制当前会话能力 | 首版重点：默认基础 Package、一个主 Package、多选 Skills/Tools、空闲修改、实际加载状态、并发隔离 |
| 资源库与安装 | 获取可供会话使用的资源 | 首版重点：下载、导入、来源风险确认、本机全局/项目安装、独立工具扩展、资源状态 |
| Package 开发 | 使用会话生产 rpi 能力 | 后续细化：工程、开发会话、测试构建、隔离验证、发布 |
| 任务与协作 | 跟踪工作并委派其他执行能力 | 后续方向：任务列表、父子关系、委派、取消、结果与产物 |
| 节点与访问 | 管理连接、共享和信任 | 后续方向：节点目录、配对、本机共享、授权撤销、远程项目/会话访问 |

此前提出的独立“Agent 管理”和“Agent 构建”不作为首版必需页面。相关能力优先落到会话资源配置和资源库；未来只有出现独立管理需求时，再设计长期 Agent 对象、定义库或部署中心。

这些能力不要求成为平级页面。主界面以项目和会话为主，资源配置、资源获取和任务等通过合适入口组合进入。

代码文件和 Git diff 只是上下文/产物的一种；研究报告、文稿、表格等也需要合理的展示方式。

### 公共交互能力

- 主 Package、Skills、Tools 的选择与来源展示；其他运行时的入口后续按能力细化。
- 本机资源安装范围选择：默认全局，可指定项目；不提前提供云节点安装入口。
- 基于实际能力与权限的入口显示、禁用原因及降级。
- 统一异步操作反馈：提交中、已接收、等待确认、完成、失败。
- 授权与待处理交互入口。
- 结果与产物查看器。
- 事件订阅、断线恢复和错误诊断。
- 后续受控 UI 扩展插槽。

## 六、运行时：外部 Agent 统一 ACP【已对齐方向】

平台上层使用统一的 **AgentRuntimeProvider**，不直接依赖每家 Agent 的命令与事件格式。

```text
Agent 管理 / 会话 / TaskService
                  │
          AgentRuntimeProvider
          ┌───────┴────────┐
    RpiRuntimeProvider   AcpRuntimeProvider
          │                   │
   rpi-extcore / RPC      兼容 ACP 的 Agent
   原生 Package 能力      Claude Code / OpenCode 等
```

- Runtime Provider 是 Agent 执行提供者，不是模型 Provider。
- 外部 Agent 的差异主要体现为启动/接入配置；不为每家各写一套平台协议。
- 实际需要的 ACP 端点、启动器或桥接程序须按版本核实，不能假设所有产品原生提供同等支持。
- 统一基础操作：能力发现、会话、输入、事件、取消、交互和资源释放。
- 恢复、配置修改、文件/终端等能力按协议协商；未实现能力不宣告支持。
- rpi Package 管理是原生增强能力，不强行塞进所有 ACP Agent 的通用接口。
- **本轮首版先做好 rpi 资源定制，ACP 资源配置后续细化。**此节描述长期接入边界，不要求首版同时完成外部运行时的资源适配。

### 会话配置与运行时绑定建议

首版不要求持久的 AgentProfile 用户对象。可先用会话配置表达资源和运行时关系：

```text
SessionConfig
├─ RuntimeBinding
│  ├─ rpi：一个主 Package + 多个 Skills + 多个 Tools
│  └─ ACP：后续按实际支持能力细化
└─ 实际加载/启用状态：从对应运行时观测
```

内部是否需要配置快照、解析结果等类型，按实现需要决定，不因此强制增加 Agent 定义库或部署流程。实际二进制路径、启动参数和凭据仍属于节点本地的受信接入配置，资源导入不自动获得这些权限。

## 七、节点对外暴露与跨节点协作【后续阶段方向】

ACP 解决“如何驱动 Agent”，不能替代节点协议。需要明确的对外层：

```text
本机客户端 ──进程内调用───────────┐
远程客户端 ──Node Gateway─────────┤
其他节点   ──Node Gateway─────────┤
                                ▼
                         NodeApi / 应用服务
                                │
                         AgentRuntimeProvider
                                │
                            rpi / ACP
```

- **Node Gateway**：入站网络接口、身份验证、协议协商、限流和事件传输。
- **NodeApi**：Agent、项目、会话、任务、产物等应用接口契约。
- **PeerClient/PeerService**：出站访问、节点信任与委派路由。
- **TaskService**：授权后的任务接收、持久化、执行和结果管理。

建议网络协作阶段采用 HTTPS 请求/响应与 SSE 事件流。本机仍可直连；网络共享显式开启，不强制本机绕 HTTP，也不要求中心服务器。这不扩展本轮“资源先只安装到本机”的范围。

### 任务协作流程

```text
A 发现 B 允许访问的 Agent
 → A 提交带幂等键、上下文范围和截止时间的任务
 → B 校验授权并落盘，返回接收回执
 → B 驱动目标 Agent 执行
 → A 订阅进度，断线后按游标恢复
 → B 提供结果和受控产物引用
 → A 将结果关联回原会话
```

执行节点掌握任务事实，发起节点保存委派记录。默认不要求 B 反向回连 A；A 可以持续查询/订阅 B。

## 八、状态与安全原则【架构建议】

- 请求已接收不等于运行完成；取消已提交不等于取消成功。
- desired、节点观测和 applied 分开；本地选择不产生节点成功事实。
- 节点断线表示离线/未知，不自动表示任务失败，不盲目重复执行。
- 任务提交幂等，事件可去重与恢复；外部副作用不承诺 exactly-once。
- 分享 Agent 调用权限不等于开放 Package 安装、配置修改或任意文件访问。
- 设备身份、节点身份、Agent 委派身份分开，不能只相信正文自报的身份。
- 委派权限只能收窄，不能自动继承全部凭据和上下文。
- 远程产物使用可授权访问的引用，不只返回对方机器的绝对路径。
- 原生 Package、工具扩展和构建脚本属于代码执行；权限声明不等于沙箱。本轮确认允许安装受信原生工具，但安装前必须明确确认来源和风险。
- UI 扩展使用宿主受控组件和动作，不开放任意前端脚本绕过权限。

节点事实包括会话历史、任务、安装和应用状态；设备本地保留草稿、收藏和外观等偏好；页面临时状态不冒充已保存状态。

## 九、代码结构演进【建议，非立即实施】

保留现有 workspace，不先重命名或大量拆 crate。多运行时共享边界明确后，可提取一个 `work-runtime`：

```text
apps/
  work-ui/          多端交互与依赖装配
  work-cli/         管理、诊断与自动化
  work-node/        后续可选的后台节点薄入口

crates/
  work-core/        领域模型、NodeApi、协议、状态机、纯校验
  work-runtime/     提取已有 AgentTransport/Session 与 rpi、ACP 适配
  work-node/        节点应用服务、Agent、任务、Package、Gateway、Peer、存储
  work-client/      本机接口句柄、远程调用、订阅恢复
  work-update/      保持独立的应用更新
```

- 复用现有运行时实现，不叠加另一套同义接口。
- `LocalWorkspace` 的节点事实管理逐步迁入节点服务。
- Client 通过注入的接口访问本机服务，不依赖具体 Node 实现，避免循环依赖。
- UI 负责交互与装配，不继续把领域逻辑堆进中心 workspace 文件。
- 同项目不同会话需要独立有效配置和并发执行，不能靠覆盖共享 `.rpi/settings.json` 切换身份；原生进程/部分启动配置隔离已验证，完整资源选择及 Work 参数透传仍是缺口。
- 首版以会话和资源为中心，不为尚无需求的长期 Agent 对象建立独立生命周期、定义库或部署中心。
- 资源状态和变化对接 rpi 的实际加载事实，不另造前端资源升级系统；不因此取消必要的应用确认、错误报告和状态区分。
- 旧设计资源不静默变成可执行包；既有 transcript 不为目录重构而重写。

## 十、建议推进顺序【按本轮优先级调整】

1. **前端需求细化**：先定义项目侧栏、新建会话、会话资源面板、已加载 Tools/Skills 展示，以及本机资源下载/导入的操作与状态。
2. **补齐 rpi 关键契约**：基于本轮验证，优先明确每会话精确资源选集、空闲应用/受控重启、配置恢复和实际资源清单；复用原生加载器与库层能力，缺失的 RPC/适配契约与上游对齐，不伪造支持。
3. **rpi 单机闭环**：新建会话默认基础 Package，可直接输入；支持一个主 Package、多选 Skills/Tools，空闲修改配置，同项目并发会话互不影响。
4. **本机资源获取**：下载/导入、来源与原生代码风险确认、默认全局/指定项目安装，并展示 rpi 实际加载结果；不增加独立会话升级流程。
5. **后续能力再细化**：ACP 的资源配置、Package 开发闭环、跨节点项目/会话访问、Agent-Agent 任务协作、UI 扩展；具体先后不在本轮强行承诺。

前端设计时保留节点身份和事件作用域。资源安装先限定本机，不抹去整体多节点方向；首版验收也不以完成独立 Agent 管理中心为前提。

具体最小数据、应用/恢复流程、上游与 Work 分工及验收顺序已整理为[会话资源配置契约提案](session-resource-contract.md)。它是待评审的实施建议，不是新增正式 API 或已有功能；先做已注册工具的窄闭环，再补精确资源选择与完整安装。

## 十一、待确认与待验证事项

### 已完成的技术核验【rpi 0.14.0 初测 / 0.15.0 复验；不是产品验收通过】

初测对象是安装的 rpi 0.14.0 和 Work 锁定的 extcore 0.1.5，23 项断言通过。后续本机宿主更新为 0.15.0，补充完整复验 **24 项断言通过，包含当前限制的负向断言**，新增空选工具语义检查；两轮证据分开记录，不冒充同一版本结果。均使用隔离的真实 RPC 宿主、真实原生 DLL 和本地确定性模型，无外部模型调用。复现、源码行号和原始证据位置见[能力验证报告](../reviews/rpi-session-resource-validation.md)。

| 验证项 | 当前事实 |
| --- | --- |
| 同项目并发配置 | 工具选择、显式 Skills/提示词启动参数可独立；`--skill` 是追加，不是排他的 Skills 选集；`--local-only` 只限制扩展，仍发现项目 Package Skills |
| 主 Package 与独立工具 | 一个项目 registry Package + 显式独立扩展已真实加载并分别执行；尚无完整主 Package 会话选择契约 |
| 空闲变更 | 已加载工具的 active 选择可以下一轮生效；Skills/Package 的 stock RPC 重载/选择入口未接通，不能把 TUI `/reload` 当 RPC 能力 |
| 零工具语义【0.15.0 补测】 | `activeTools=[]` 时模型仍收到全部注册工具；现有空数组不能表达“全部关闭” |
| 历史续用 | 同 ID 重启后更换 Skills/提示词或显式原生扩展集合，可保留并续用旧历史；不等于旧上下文清除或完整 Package 切换事务 |
| 配置恢复与刷新 | 运行时工具选择在重启后恢复启动默认；新增 Skill 在新宿主可见，旧宿主未自动发现；必须单独处理配置保存、重应用与确认 |
| 资源事实与冲突 | Tools 名称/active 状态可读；缺 Skills 清单；Skill 同名时项目优先；提示词列表出现不代表本轮已使用 |

库层已有 `set_resources`、`set_tools`、`set_system_prompt` 和 CLI 资源重载例程；缺口主要是可依赖的 RPC/会话配置及 Work 适配，不应另写一套资源加载器。Work 生产通用扩展管理仍为 Unsupported，不能用隔离 demo 结果宣告已交付。

### 尚需补齐或进一步验证的技术事项

- 每会话的完整 Package/Skills/扩展有效选集，以及防止项目/全局自动发现混入未选资源的契约；不能只靠 additive `--skill`。
- 空闲变更采用库层重载还是受控重启；忙碌校验、配置持久化、恢复前重应用、失败回滚和加载确认如何协作。重启的底层可行性不等于产品已批准该方案。
- 宿主如何提供实际资源来源、加载错误、active/model-visible 状态；Skill 本轮读取/使用需要另有证据。
- Package 附带 Skills/Prompts/Themes 的安装分发：本轮只证明安装目录中的 Skill 会被发现，没有证明 `package link` 会复制源目录的这些资源。
- 本机全局安装、网络下载、来源确认和失败恢复的完整闭环；本轮项目原生安装已实测，全局路径仅源码核查，网络未测。
- 文档中的 `settings.packages` 不能代替加载证据：当前参考源码消费项目包 registry，未见该 settings 字段的加载实现；不要把未知字段保留误判为功能支持。

### 产品细节与后续阶段

- 默认基础 Package 的具体内容、来源，以及首次使用所需的宿主和模型准备流程。
- Skills/Tools 选择器的具体形态、默认选择，以及安装完成但宿主尚未加载时的反馈。
- 会话重命名、归档、删除、置顶、导出等操作，哪些是节点状态，哪些是设备偏好。

## 核心共识摘要

> **首要价值是用 rpi 资源定制并使用不同用途的会话，不限于编码。新建会话默认基础 Package；不要求先创建长期独立 Agent。**
>
> **每个会话是一个主 Package + 多个 Skills + 多个 Tools。同项目会话必须并发隔离；配置可在空闲时修改，保留历史并影响后续执行。**
>
> **资源支持界面下载、导入；先只安装本机，默认全局、可指定项目。独立工具扩展不算第二个主 Package；原生代码须确认来源与风险。**
>
> **加载事实以 rpi 为准，不另建会话资源升级流程；已验证工具切换、部分启动参数隔离和重启续用历史，但精确资源选集、RPC 重载、配置恢复及 Skills 清单仍需补齐。**
>
> **底层按 Node 隔离项目与会话；侧栏按 Project 平铺，通过远程标识与悬浮信息表达节点归属。**
>
> **外部 Agent 统一 ACP、节点对外 Gateway、跨节点任务协作仍是总体方向；ACP 资源配置后续细化，跨节点协作不合并原生会话。**
